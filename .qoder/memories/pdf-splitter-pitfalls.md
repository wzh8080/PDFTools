只记本项目会踩的坑。通用教训（实证核验、并发兜底、状态残留、Windows shell 陷阱等）在全局层，
本文件不复制其措辞，但为了让记忆随 git 迁移，这里保留必要的完整表述。

## 1. `/Rotate` 继承与净角度陷阱

- 读可继承属性用 `page.node.getInheritableAttribute(PDFName.of('Rotate'))`；手动遍历 `page.node.Parent()`
  只查一级，会漏掉深层继承的旋转值，导致方向判断错。
- 「是否需要重存」的判据必须是**并集**（某页 `声明 /Rotate ≠ 0` 或 `userRot ≠ 0`），不能看合成后的净角度。
  pdf.js 的 viewport 会自动应用 `/Rotate`，而 pdf-lib 的 `getSize()/embedPage()` 完全忽略它，
  于是声明 90 + 用户 270（净 0）若走「复用原始字节」分支，预览按旋转后方向显示、切分仍按原始坐标算，
  两引擎坐标系不一致 → **裁错栏**。净 0 也要重存，目的是把 `/Rotate` 剥离进页面几何。
- 推论：同一份 PDF 被两个行为不同的库共同消费时，任何「叠加后为零就跳过」的优化都按同一方式排查。

## 2. 内容检测的测试数据会自己造假

用脚本合成 PDF 验证「按纵向墨迹投影分栏」时，若每行 `drawText` 用**完全相同的字符串**，
字间空格会在纵向上严格对齐，形成一条贯穿上下的**假白色竖沟**，把每栏内部又切碎再被 `minGap` 合并，
得到的区段结构与真实试卷完全不同。必须让每行文本随行号变化（逐行不同字符序列）。

另两个污染源：Helvetica 标准字体不能编码中文，样例一律用 ASCII；同一 `http.server` 端口反复导航
不会绕过浏览器对样例 PDF 的资源缓存，读数看似「1 栏 / 2 栏」其实是旧文件 —— 用
`fetch(url, {cache:'no-store'})`、换文件名或加时间戳查询串。
读数和源码规则冲突时，第一动作是打印中间量（merged bands / cuts）确认，而不是改代码或怀疑实现。

## 3. 并发识别不能有任一子任务 reject

`detectAllCols()` 用 `Promise.all(每页 analyzeCuts(i))` 收集 `state.cuts`，之后才调 `updateOverlays()`。
若某页渲染 / `getImageData` 抛错且未被捕获，整批 reject → 界面更新根本不执行 → **UI 静默停在旧分割线，
控制台也不打印**，表现为「改了没生效 / 一直回退」。所以 `analyzeCuts` 必须内部 `try/catch` 且
`catch` 分支 `return` 可用兜底值（回落到 `detectCols()` 比例启发），外层再挂 `.catch` 记录日志。

## 4. 前端改了但真机没变

`pdf-splitter/` 的任何改动都必须重新 `assembleDebug`（`:app:syncWebAssets` 在 `preBuild` 阶段
把源码同步进 `assets/www/`）才可能在设备上生效；APK 内仍是旧版本时真机测试等于没测。
部署前应解包核对 `assets/www/app.js` 里确实含本次新增的标识（例如 `pv-rot-l`、`btn-rot-all-left`、
`data-rot="270"`），并确认旧元素（如 `pv-tip`）已无残留。

## 5. 阈值仍未经真卷验证

`0.45 / 0.02 / 0.03 / 0.16 / 12%–88%` 这组内容检测阈值是对**合成样例**调出来的（见第 2 条）。
紧密排列或极淡沟的真实扫描件可能需要重调。设备上装的是哪版包、以及真卷复验，都还是未闭环项。

## 6. 验证结论容易被残留状态污染

在同一个已打开页面里连续跑多组断言时，前一组对全局状态的修改会带进后一组：
实测过「上一轮点过模式按钮使 `data-mode` 停在 `3`，随后加载新样例读到『将生成 3 页』」被误当成
自动识别的输出。任何行为断言前，先把被测状态显式归位并**在同一轮返回值里回读确认**
（当前 active 按钮的 `data-*`、实际生效参数），把前置状态证据和结果证据一起返回。
同理，删除临时产物的工具返回 success 只代表请求受理，须用 `Test-Path` / `git status` 二次复核。
