用户在 2026-09-30 明确说「暂时不做修改」。以下三点已分析完、方案已给，等他下次点头再实施。
（原文来自旧机器 Qoder-Daily 工作区的项目记忆，因当时是从 Daily 目录改 pdf-splitter，故记在那边；
现已整合进本仓库。）

**1. README 里「上下边距决定放大率」这句措辞不严谨。**
缩放是 `Math.min(aw/栏宽, ah/栏高)`，谁小谁说了算，与边距只是「边距」的直觉无关。竖栏 +
左右 ≤14.2 mm 时确实由上下决定；但选「不切分」处理横版原页永远由左右决定，左右超过临界值也会
反过来。2026-09-30 已把**界面上**那行「边距＝…；微调＝…」说明整行删掉（提交 `479653c`），
README 的同句表述仍待处理。备选：A 只改 README 文案；B 按当前栏形动态显示「受哪个方向限制」
（约 8 行）；C 不动。

**2. 预览预热（把切分时的逐页栅格化挪到用户调参数的时间里）。**
实测单页首次栅格化 ~0.5–1 s 且与目标分辨率无关（300/500/820 px 都是 ~975 ms），所以降分辨率
无效，只能提前画。用户提议上限 20 页，可行，但要三条护栏：页数 ≤20 **且**累计 canvas 像素
≤~25 兆像素（A3 三栏单页 canvas 约 3.8 MB，只卡页数会到 ~76 MB）；加载后先画首屏、空闲约
600 ms 再起队列、页间让出主线程；按下切分时暂停、换文件时丢弃。局限：收益取决于用户在设置页
停留多久，是「挪走等待」不是「消灭等待」。

**3. 切分时把检测位图直接画进预览 canvas（而不是画完即丢）。**
总耗时不变，但「调边距后重新切分」的第二遍完全免费。代价是等于把整份文档都画出来，内存问题
与第 2 点同源，所以要不要一起上取决于第 2 点的像素预算怎么定。

**Why:** 这三点都是性能/表述权衡，不是 bug；用户习惯先看分析再决定，且明确说过并发方案那次
「噪声压过收益就撤掉」，说明他要的是可证明的收益而不是复杂度。

**How to apply:** 下次他提起切分慢、边距文案、或要优化 pdf-splitter 时，直接从这里取对应方案
与数字，不要重新做一遍测量。若栅格化实现或 pdf.js 版本换代，~975 ms 与 3.8 MB 两个数字需重测。
